# Задание 5. Интерфейс или абстрактный класс

## Identifiable

Выбор: interface.

Мотивировка: это способность с одним методом `id()`. Её могут иметь несвязанные классы (`Course`, `Student`, `Offer`), общего состояния и общего базового класса у них нет. Класс может реализовать сколько угодно интерфейсов и при этом наследовать другой класс.

Цена изменения: новый абстрактный метод в интерфейсе ломает все реализации. Смягчается default-методом, но поведение по умолчанию должно подходить всем.

## CoursePolicy

Выбор: interface.

Мотивировка: это стратегия допуска с несколькими независимыми реализациями (возраст, prerequisites, вместимость) без общего состояния. Клиент зависит только от контракта, а реализации подменяются без правки клиента, в том числе лямбдой.

Цена изменения: новый метод в контракте требует правки каждой политики. Чтобы этого избежать, контракт делают минимальным (один метод), а новые возможности добавляют отдельными интерфейсами.

## BaseEntity

Выбор: abstract class.

Мотивировка: у всех сущностей есть общее состояние (поле `id`) и общая логика `equals`, `hashCode`. Интерфейс не может хранить поля, а повторять этот код в каждом классе значит дублировать его. Все наследники действительно являются сущностями (отношение «является»).

Цена изменения: наследники жёстко привязаны к базовому классу. Изменение поля или `equals` затрагивает все подклассы, а наследовать другой класс они уже не могут, так как в Java одиночное наследование.

## Formatter

Выбор: interface.

Мотивировка: один контракт `format(...)` и разные реализации (`CompactCourseFormatter`, `DetailedCourseFormatter`) без общего состояния. Интерфейс позволяет хранить реализации в одном массиве и добавлять новые, не меняя клиентский код (задание 3).

Цена изменения: новый метод в интерфейсе затрагивает все форматтеры. Если нужен общий код (например, проверка входа), его выносят в абстрактный класс-заготовку поверх интерфейса, как `AbstractNotificationSender` в задании 4.

## ClockProvider

Выбор: отсутствие отдельного типа, используется `java.time.Clock` из JDK.

Мотивировка: `Clock` уже решает задачу получения текущего времени и легко подменяется в тестах фиксированными часами (`Clock.fixed`). Собственный интерфейс с методом `now()` только повторил бы его.

Цена изменения: если понадобятся доменные методы (учебная неделя, начало семестра), придётся ввести свой интерфейс и заменить все использования `Clock`. Пока этого нет, лишний тип не нужен.
